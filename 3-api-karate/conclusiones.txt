=====================================================================
 CONCLUSIONES - EJERCICIO DE APIS (SIGNUP Y LOGIN DE DEMOBLAZE)
=====================================================================

QUÉ HICE
Primero probé el registro y el login a mano en la página y revisé con las herramientas
del navegador (F12) qué datos se envían al servidor y qué responde. Así descubrí, por
ejemplo, que la página envía la contraseña codificada en Base64. Con esa información
automaticé los 4 casos pedidos con Karate: crear un usuario nuevo, intentar crear uno
que ya existe, login correcto y login incorrecto. Los datos de prueba están en archivos
JSON y CSV, y los 7 escenarios pasaron.

Cada ejecución crea usuarios con un nombre único (prefijo + hora), porque al probar a mano
me di cuenta de que casi cualquier nombre común ya está registrado en Demoblaze.

HALLAZGOS
1. La API acepta registros con campos vacíos (defecto): la página no deja registrarse
   con los campos vacíos, pero revisando con F12 vi que esa validación la hace solo la
   página. Al probar directamente contra la API encontré que:
   - con la contraseña vacía, el servidor registra el usuario igual, sin contraseña;
   - con el usuario vacío, el servidor se cae y responde un error 500.
   Esto es importante porque cualquiera que use la API directamente puede saltarse la
   validación de la página. Dejé estos casos marcados como @defecto para poder
   reproducirlos (ver readme.txt) y guardé la evidencia en la carpeta reportes.
2. El login da mensajes distintos según el error: "Wrong password." si el usuario
   existe y "User does not exist." si no existe. Con eso cualquiera puede averiguar
   qué usuarios están registrados. Lo recomendable es un mensaje único como
   "Usuario o contraseña incorrectos".
3. Todas las respuestas devuelven el código 200 (éxito), incluso cuando hay un error.
   Para saber si algo falló hay que leer el mensaje de la respuesta, lo que hace más
   difícil detectar errores.
4. No hay reglas para las contraseñas: se puede registrar un usuario con "123456".
5. La contraseña viaja codificada en Base64, pero eso no es cifrado: se puede decodificar
   fácilmente. La seguridad depende solo de que la conexión sea HTTPS.
6. Hay un error de redacción en el mensaje "This user already exist." (debería decir
   "already exists").

CONSIDERACIONES Y DECISIONES
- Puse la URL y las funciones comunes en karate-config.js para no repetirlas en cada
  archivo; si la URL cambia, se edita en un solo lugar.
- Creé un archivo de apoyo (crear-usuario.feature) que crea un usuario y que reutilizo en
  varias pruebas. Así las pruebas de login no dependen de usuarios que existan de antes.
- Ejecuto las pruebas de una en una porque Demoblaze es un ambiente público compartido.

QUÉ MEJORARÍA
- Validar también la estructura de las respuestas y los tiempos de respuesta.
- Probar más casos límite: caracteres especiales en el usuario, textos muy largos, etc.
